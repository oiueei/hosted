# OIUEEI Frontend Documentation

React frontend using HDS (Helsinki Design System) from npm with OIUEEI customization layer (fonts, colors, icons). Vite dev server on `localhost:3000`. All API requests are proxied to the Django backend on `localhost:8000`. All UI strings are externalised via `react-i18next` (British English, `src/i18n/locales/en.json`).

**Public read of PUBLIC collections (anonymous visitors):** `/collections/:code`, `/collections/:code/things/:thingCode` and `/things/:thingCode` sit in the **public** route block (outside `RequireAuth`). The backend's `can_view` gates them, so only PUBLIC, ACTIVE collections are readable without a session. When unauthenticated, `CollectionPage` shows the thing **action buttons as usual** (via `ThingLinkbox`'s `loginToAct` prop — passed `!isAuthenticated`): the cards look the same as for a member, but each action's click (Claim / Buy / Rent / Borrow — the per-type verbs in `thingCard.action`) **navigates to `/collections/:code/join?thing=<code>`** (`JoinPage`) instead of performing it. (The `JoinToAct` component now renders only inside `JoinPage`.) It was removed; the strings went with it. What was left is exactly the action-button path above, which needs a card to click — and that left two places with no door for a signed-out reader: an **empty PUBLIC group** (the empty state used to fall back on this hero link, and the curator's own share menu points readers there) and the bottom of a **COMMUNITY** one, where to *contribute* you had to press "Request" on somebody else's thing. In **every** public group, COMMUNITY or PROPRIETARY, empty or not — which also gives a **member with no session** (the weekly digest's link is an ordinary one, and an expired session lands here too) a way in from the page itself. ## Page Titles

Every page sets `document.title` via `useEffect` for meaningful browser tab titles and bookmarks. Dynamic pages (CollectionPage, ThingPage, UserPage, etc.) update the title when data loads. Format: `{Page context} — OIUEEI` — and `test/i18nParity.test.js` checks every `titles.*` string in the three locales ends with it (`titles.reserveThing` was the one that forgot, in all three, until 2026-09-29).

## Page Layout Pattern

All pages use a consistent `form-hero` + `Koros` layout (the HDS Hero component is not used):

```
form-page
├── form-hero          (full-width, theeeme color_03 background)
│   ├── form-hero-content  (max-width 1248px, text color from --hero-text-color CSS var using theeeme color_05)
│   │   └── [back link, title, description]
│   └── Koros          (HDS Koros component, type from user.koro preference, 60px height, fill = theeeme color_02)
└── page-container     (max-width 1248px, page content)
```

**The page is a column as tall as the visible screen, with the footer at the bottom of it.** `.form-page` used to carry `min-height: 100vh` and the footer came after `<main>`, so every page was a screen plus a footer: always a scroll, even for a short page, and the footer always just under the first screen — and on iOS Safari `100vh` is taller than what is visible (it counts the browser's bar), so the page overflowed even when it fitted. Now, in `App.css`: **`#root`** is a flex column with `min-height: 100vh` and, after it, `min-height: 100dvh` (the visible height, for whoever understands it; `100vh` stays as the line for the rest) — `#root` and not a wrapper in `App.jsx`, since the skip link, `<main>` and the footer are its children and no element had to be added; **`main`** takes what is left (`flex: 1 0 auto`) and is itself a column; **`.form-page`** lost its `min-height` and grows to fill `<main>` (`flex: 1 0 auto`), so its `color_02` (inline) reaches the footer with no strip of another colour between them; and **`main > .page-container { width: 100% }`**, because a bare `.page-container` straight under `<main>` (the loading spinner, Home's offline banner) has `margin: 0 auto`, which in a column flex container stops it stretching. Result: a short page has no scroll and the footer is at the bottom of the screen; a long one has the footer after its content. The footer itself did not change. Pinned in `test/stickyFooter.test.jsx` with the helpers of `test/cssRules.js` (what the rules declare, that `100vh` and `100dvh` each appear once in the stylesheet and nowhere in code, and the DOM the rules are written against: `<main>` and the footer siblings, the footer after `<main>`, the skip link before it); jsdom does no layout, so how it looks was checked once in Firefox (headless, the real `App.css` over a simplified DOM: a short page `scrollHeight` = `innerHeight`, footer at the bottom, no strip; a long one, footer right after the content), **not on an iPhone**.

**Site footer (i14):** a global one-line colophon (`SiteFooter`, mounted once in `App.jsx` after `<main>`): "Made with ♥︎ in Zona Franca, Barcelona, Catalonia, Spain, EU" (`footer.madeIn`, ×3 locales). Painted with the viewer's theeeme `color_02` (same token as `.form-page`'s background) so there is no colour seam, and pinned to the bottom of the visible screen on a short page (see "The page is a column…" above); `useLocation()` re-renders it per navigation so a theeeme change is picked up. The heart is U+2665+U+FE0E (text presentation — inherits colour, never a red emoji). **It also carries links** (`footer.legal` → `/legal` always; **`footer.contact` → `/contact`** (or, where the deployment hosts a form for it, `externalForms.contact` in the reader's language, in a new tab; see the `deployment/` table), the third door since 2026-10-04 — it was a speech-bubble icon in the corner of every hero, and there were too many icons up there; `footer.about` → `deployment/aboutPath` only where that deployment has a page saying what it is — upstream it is null and the link is absent, since a footer link to a 404 is worse than one link fewer). `/legal` is the page the privacy claims say to go and check, and every link to it used to sit behind a login or on a page only a joiner sees, so someone reading a public collection — the top of the whole funnel — could not reach it. Plain text links, not a nav block. **One line from 768px:** "What OIUEEI is · Privacy & legal · Contact us · Made with ♥︎ in …" — the `<nav class="site-footer-links">` still holds only the links (it is a landmark) and the text stays outside it, with a separator `·` between them (`.site-footer-sep`, `aria-hidden`, spaced like the dot between the links) that App.css shows only from 768px: the column becomes a flex row, `align-items: center` because the links are 44px tall and the text is not, `flex-wrap: wrap` only as the way out of a language too long to fit, and the nav loses the bottom margin that was the gap between the two lines. **Under 768px**: two lines, the doors over the text, and the separator `display: none` because on two lines it would hang at the end of the first. Upstream, with no about link, it reads "Privacy & legal · Contact us · Made with ♥︎ in …". **Aligned to the left of the content column, not centred:** `.site-footer` keeps the full-width background and `text-align: left`, and an inner **`.site-footer-inner`** holds the page's own column — `max-width: 1248px`, `margin: 0 auto` and the same side padding as `.page-container` — so the first letter falls on the vertical of the headings and the text above it; from 768px that column is the flex row with `justify-content: flex-start` (it was `center`), and **the first link has no padding on its left** (`.site-footer-links a:first-child`) so that letter is exactly on the vertical. The links keep `padding: 0 var(--spacing-2-xs)` and their 44px. Pinned in `test/siteFooter.test.jsx` (the three doors and their order, in both shapes of deployment; the separator `aria-hidden` and outside the nav; the column's width, centring and padding against `.page-container`'s; `justify-content` and `text-align`; the first link's padding) with the helpers of `test/cssRules.js`; not seen in a browser. Plain text links, not a nav block. **Deliberately not HDS `Footer`** (a recorded exception to DESIGN §1, not an oversight): that component is a full navigation block with link columns, a logo row and a back-to-top control — this is one line of colophon, and adopting it would import the site-map footer OIUEEI has no content for (DESIGN §3: ask what can be removed).

**The hero's icon corner:** up to **three** icon-only controls share the hero's top-right corner, in one `.hero-corners` flex row (App.css) rather than each computing its own absolute offset — `AccountMenu` first (any signed-in visitor), then `CollectionMenu` (`CollectionPage` only: curators, and since 2026-10-04 **members**, each with what is theirs — see its note), then `ShareCollectionMenu` (`CollectionPage` only: curators, **and any member of a PUBLIC group** — 2026-09-29, see below). **There was a fourth, `ContactCorner`, last and for everybody — a speech-bubble link to `/contact` — until 2026-10-04** (there were too many icons up there): it, its `.contact-corner` rule and `contact.linkLabel` are deleted, and "Contact us" is the third door of the site footer. `gap` never reserves space for a control that isn't rendered, which is what makes the row correct for a member (no collection menu, and no share menu in a private group) and for a signed-out reader (the account icon as a "Sign in" link, and neither collection menu nor share menu) without each control needing to know what else might be missing — the old per-icon `right:` offsets could not have absorbed a third, session-gated icon without every existing offset also depending on whether *that one* was present. `.hero-corners` is rendered as the first child of `.form-hero-content` (so `--hero-text-color` resolves and its contents stay visible on dark theeemes, like the back link) and is itself absolutely positioned against `.form-hero` at the content column's right edge. Inserted in `PageLayout` plus the 8 manual-hero pages (`test/heroCornerLayout.test.jsx` pins that none of them links `/contact` from it, and that nothing in the sources names the old component).

**Keeping out of the corner at 320px (2026-09-29).** `.hero-corners` is absolute and reserves nothing, so a long "← {collection name}" — the first line of `ThingPage`, `RequestThingPage`, `EditThingPage`, `DeleteThingPage`, `ManageInvitesPage`, `JoinPage`… — ran underneath the icons. `.form-hero-content .back-link` is now capped at `calc(100% - var(--hero-corners-width) - var(--spacing-xs))` so the text wraps before the icons; `--hero-corners-width` (defined on `.form-hero-content`) is the widest the row gets, a curator's hero on `CollectionPage` — 3 controls of 44px plus 2 gaps, 148px (4 and 200px between the collection menu, 2026-10-03, and the contact icon leaving, 2026-10-04) — and **every** hero reserves it, since a back link cannot know which icons its page will render (a member's or a signed-out reader's link is narrower than it strictly needs to be — the known price of a corner whose icons the back link cannot predict). The heroes whose first element is the `<h1>` (`NotFoundPage`, `VerifyPage`, `HomePage`, `LoginPage`, `DigestMutePage`) may rub against the icons in the same way and were **left alone**: without seeing a screen it would be CSS on faith. `test/heroCornerLayout.test.jsx` pins the contract rather than the pixels (jsdom does no layout): the selectors match the DOM the pages paint, and the reserved width is recomputed from that DOM (3 controls) and from the widths the controls declare, so adding a fourth icon or resizing one goes red until the variable follows.

**Account menu:** `AccountMenu` (`src/components/AccountMenu.jsx`) puts the account's own pages — "My profile" (`/me`), "My requests" (`/my-bookings`), "Requests to me" (`/owner-bookings`, only for an account that can receive requests — see below) and "Log out" (`/logout`), plus "Home" (`/`) at the top — one click away from **every** hero, not only `/` and `/me`. **A sweep enforces it** (`test/themedButtons.test.js`, 2026-09-29): every HDS `<Button>` opening tag in `pages/` and `components/` must carry a `style=`, a spread `{...}`, or `variant="supplementary"` / `variant="danger"` — the icon-only buttons and the account-erasure confirms, which are the two written exceptions. ## Breakpoints

OIUEEI follows the official [HDS breakpoint tokens](https://hds.hel.fi/foundation/design-tokens/breakpoints/). HDS defines six breakpoints; OIUEEI uses four of them and intentionally skips `breakpoint-s` (576px) and `breakpoint-xxl` (1440px). Use only these exact `min-width` values in media queries — never use arbitrary pixel values.

| Token | Min-width | Container width | HDS grid columns | Margin |
|---|---|---|---|---|
| `breakpoint-xs` | 320px | 288px | 4 | 16px |
| `breakpoint-m` | 768px | 720px | 8 | 24px |
| `breakpoint-l` | 992px | 944px | 12 | 24px |
| `breakpoint-xl` | 1248px | 1200px | 12 | 24px |

The `page-container` and `form-hero-content` max-width is **1248px** (aligned with `breakpoint-xl`). The complementary `max-width: 767px` query (below `breakpoint-m`) is also valid for mobile-only overrides.

**Wide content scrolls inside itself, never the page body.** `hds-react` ships `.Table-module_container { height: inherit }` and no `overflow-x`, so a native `<table>` sizes to its content and pushes the body past the 288px xs container. Every HDS `Table` therefore sits in a **`.table-wrap`** (`overflow-x: auto`, App.css) — `ManageInvitesPage`'s directly, and the request tables and "My groups" through `ResponsiveTable`, which adds it on a desktop. **Below 768px those last three stop being tables at all** and become a list of cards: at ~100px a column, names broke word by word, the status labels were cut off on the right and the ✓ ⊗ buttons sat beyond the screen's edge with nothing to say the table scrolls. Markdown pipe tables in a bio have their own `.markdown-table-wrap` for the same reason. No `tabindex` on either: the rows carry links and buttons, so a keyboard reaches the off-screen columns by tabbing in. Those three pages' **actions column** (the row's buttons, no visible heading) carries a screen-reader-only header, `common.colActions` ("Actions") in a `.sr-only` span — HDS renders a non-sortable `headerName` as the `<th>`'s child, so a node works; it was `''`, an empty `<th>` axe flags as `empty-table-header` (2026-09-18).

### VerifyPage (`src/pages/VerifyPage.jsx`)

- **API:** `GET /api/v1/auth/verify/{code}/` (resolve) and `POST` of the same URL (commit a booking decision).
- Fetches (GET) on mount using the `:code` route parameter.
- **Booking accept/reject — one-click auto-commit:** when the GET returns `requires_confirmation` (a `BOOKING_ACCEPT`/`BOOKING_REJECT` preview, no mutation), the page **immediately fires the committing `POST`** from within the load effect, showing the "Verifying…" screen until it resolves to the confirmed/rejected success screen. The owner's single click (opening the email link) is enough — no second on-page button. Safety is preserved because the commit only runs from **real JS execution**: an email link-scanner or prefetch does a bare GET, runs no JS, and so still can't decide a hold (the backend also refuses to commit on GET). A `committedRef` guard stops React 19 StrictMode's dev-only double-invoked effect from POSTing twice.
- **ACCOUNT_DELETE is the exception to the auto-commit**: when the GET preview's `action` is `ACCOUNT_DELETE`, the page renders a dedicated confirmation screen (account email, owned collection/thing counts, the what-stays line) and the committing POST only fires from the explicit **"Delete my account forever"** danger button — never from the load effect. On success it clears `userCode`/`theeemeColors`/`koro` from localStorage and shows the goodbye screen (`verify.accountDeleted*`); a Cancel button exits to home/login.
- On `COLLECTION_REJECT` action: shows success `Notification` confirming the invitation was declined and the owner was notified. Shows "Go to login" button. No login/redirect.
- On success: stores `userCode` in `localStorage` (and the theme colours and koro from `data.user`) **and applies the account's saved language** — `data.user.language`, if it is one of `SUPPORTED_LANGUAGES`, with `await i18n.changeLanguage(...)` **before navigating** and persisted like the profile's own Select (the symptom was "English" saved, link opened on a phone, app in Spanish). `App.jsx`'s mount effect that applies it runs once, and opening a magic link mounts the app before there is a session (its `/auth/me/` is a 401). Empty ("Automatic") or unknown ⇒ untouched; a failed language load never fails the sign-in. **The verify effect does not depend on `t`**: a language change gives `useTranslation` a new `t`, and an effect that redeems a single-use link must not run twice (it showed an error to someone who had just signed in, and looped). Auth tokens are set as HttpOnly cookies by the backend. **The destination comes from the backend's `landing` field** (see `core/views/CLAUDE.md` → VerifyLinkView): `collection` ⇒ `/collections/{data.collection || data.invited_collection}`, **`path` ⇒ `data.path`** (the page the login was asked from, `next`; re-checked with `safeNextPath` because it is handed to the router, and one that fails falls through to `/`), anything else ⇒ `/` — a `welcome` landing included: there is none since 2026-10-04 (the server answers an open door's visitor from the groups they have, like anyone else), and an unknown one just goes home. It used to be decided here from a `seenWelcome` localStorage flag, but `LogoutPage` cleared that key, so every re-login looked like a first visit; moving the decision to the server is what fixed it, and the flag is gone entirely now that the collection welcome box it fed is too.
- On failure: shows error `Notification` with helpful guidance and "Go to login" button (resolves dead-end for expired links). **A 403 carrying `code: "no_longer_manages"` is not one of those either (2026-10-02)**: a co-curator demoted after the email pressed the old link; the server rightly refused, burnt the link and left the request pending, and `VerifyPage` says `verify.noLongerManages` ("You no longer run this thing, so this link can no longer decide the request.") with **no** `expiredHelp` line — advice about asking whoever invited you has nothing to do with it. Without the code a 403 reads as before. **A refusal carrying `retryable` is not one of those**: an approval blocked by the invitation quota or the member ceiling leaves the link working, so the page shows the server's own reason and `verify.refusalHelp` ("this link still works") instead of `verify.invalidOrExpired` + `expiredHelp`. Every other refusal here consumes its RSVP, which is why the expiry copy stays right for them.

It moved to the own profile's "My groups" list (`UserPage`): leaving is something you do to your own membership, so it belongs with the rest of your account, next to the other memberships you might weigh it against. The route (`/collections/:code/leave`) and `LeaveCollectionPage` are unchanged. A curator is refused this route server-side (2026-09) — a co-owner leaves by being demoted, not by self-unlinking — and the button never offered itself to one anyway, since it keys on `is_member`.
- **Inactive things section**: below the Things section, when the payload carries at least one `INACTIVE` thing. Gated on the payload rather than `isOwner` (2026-09): the backend now sends an INACTIVE thing to the collection owner (every one) **and** to that thing's own owner (just theirs), so a COMMUNITY member's own contribution — a completed gift, or a listing they hid themselves — stays reachable here instead of only via its standalone `/things/{code}` URL. ### RequestThingPage (`src/pages/RequestThingPage.jsx`)

- **APIs:** `GET /api/v1/things/{thingCode}/` (detail — **with `?collection={code}` on the collection-context route**, so the rules the form is built from are that collection's, the same one the POST names in `collection_code`; see `ThingSerializer` in `core/serializers/CLAUDE.md`), `GET /api/v1/things/{thingCode}/calendar/` (blocked periods for date-based types), `POST /api/v1/things/{thingCode}/request/` (submit request)
- Accessible from `/collections/:code/things/:thingCode/request` (collection context) or `/things/:thingCode/request` (standalone).
- Redirects to `/login` if no `userCode` in `localStorage`.
- **Back link**: uses `location.state.backPath` and `location.state.backLabel` passed from ThingLinkbox or ThingPage.
- **Page title**: `Hold: {thing.headline}` with fee display when present.
- **The collection's request-page note** — a Markdown-editable note the owner writes once for the whole collection (`Collection.request_info`, set in Create/Edit under "More options", `LocalizedInfo variant="requestInfo"`), shown for **every** date-based verb reaching this page (LEND/RENT/RESERVE), not RESERVE_THING only. Read via `thing.collection_request_info` (resolved through `useLocalized`'s `L`) and passed as `PageLayout`'s `description` prop, rendered via `<MarkdownText>` — `PageLayout` renders `description` in a `<div className="form-hero-text">` rather than a `<p>` specifically so Markdown's block-level output (lists, headings) is legal there. Absent (`undefined`) when the collection has no note, so nothing renders.
- **Form fields** adapt to thing type:
  - `LEND_THING`, `RENT_THING` — `DateInput` for start and end dates with blocked-date validation. **In its free form (no fixed lengths) the two pickers follow the server's rules: the collection's weekdays and the chained handovers** (`freePickupDisabled` / `freeReturnDisabled` in `utils/rental.js`): a booking `[s, e]` occupies the pickup on `[s, e)` and its return day `e` is free for the next pickup, and a request `[start, end]` conflicts only if it shares an interior day with a booking (`BookingPeriod.has_overlap`: `s < end AND e > start`, the same strictness as `compute_availability` and the card's "available from …"). So the **pickup** picker is out on `[s, e)` of every booking and on closure days; the **return** picker is judged against the pickup chosen so far — out before the pickup, out on a closure day, and out when the stretch `[pickup, return)` runs over a booking (`rangeBlocked`, where touching a booking's pickup is a chained handover and stays open); the pickup's own day is a same-day return, and with no pickup chosen yet the return follows the pickup's rule. Both pickers used to grey out BOTH ends of every booking (`isDateBlocked`, the calendar *display* range, now deleted), which blocked picking up on another booking's return day and returning on another's pickup day, though the server allows both: a card said "available from 06/10" and the calendar began on the 7th. **The weekdays:** `freePickupDisabled` and `freeReturnDisabled` take `rentalWeekdays` (the collection's `rental_weekdays`, Python's 0 = Monday, `[]` = any day; the page passes the one it already computes from the thing) and a day of a weekday that is not allowed is out in **both** pickers — in the return picker whether or not a pickup is chosen, since the weekday does not depend on it. The server demands them at both ends with or without fixed lengths (`Collection.rental_violation`: `rental_pickup_weekday` for the pickup, `rental_return_weekday` for the return), and the free form once did not apply them: a Wednesday could be picked in a "Saturdays only" collection and was refused on send. The two rules add up: a Saturday that a booking occupies is still out, and its return day (a Saturday too) is still the chained handover. The fixed-length and RESERVE forms already used `isPickupDisabled` / `reservationPickupDisabled`. No client-side overlap check exists at submit; the server's 409 stands. Pinned in `utils/rental.test.js` (both helpers, both clock changes, the weekdays at both ends) and `test/requestRental.test.jsx` (the real HDS calendars, a 06→08 request after a 05→06 booking, and a "Saturdays only" collection in both calendars). **Rental rules (#7):** when the thing's collection defines `rental_durations` (from `ThingSerializer`), the free start/end pickers are replaced by a **duration `Select`** (the collection's fixed lengths) + a single **pickup `DateInput`**; the return date is derived (`pickup + length`, shown as "Return by …" — a one-week rental picked up on a Wednesday returns the NEXT Wednesday, so a single allowed weekday stays satisfiable). The pickup picker (`isPickupDisabled`, via `utils/rental.js`) disables days whose weekday — or the computed return day's weekday — isn't in `rental_weekdays`, and any day whose range overlaps a booking. The request POSTs `collection_code` so the backend applies the right collection's rules.
  - `RESERVE_THING` — **two flows, chosen by `thing.reservation_unit`, never both.**
    - **`DAY`** (the original shape) — **pickup date + duration in days** (1..`thing.reservation_max_days`; the duration `Select` is omitted and the length fixed to 1 when the cap is 1), plus an optional **`project_note` `TextArea`** (≤512). The date picker's `maxDate` is `today + thing.reservation_horizon_days` (the collection's own limit, not the fixed 90 the rental picker uses) and its `dateOutsideRangeErrorText` names that number (`reservation.dateRange` with `{days}`, not the generic `request.dateRange`'s hardcoded 90). A `reservation.pickupHelper` line under it says closed/booked days are greyed out (the member sees a half-dead calendar and, without it, no reason). Pickup picker uses `reservationPickupDisabled` (`utils/rental.js`) — stricter than `isPickupDisabled`: **every** day of the span must be an allowed weekday, since the space can't be booked across a closed day. When the length is more than a day and a pickup is set, a `reservation.dateSummary` line shows the inclusive span it will book (`start` … `start + duration − 1`) — the reservation auto-confirms, so there is no owner step to catch a wrong end. POSTs `{ start_date, duration_days, project_note, collection_code }`.
    - **`HOUR`** — day first, **then** duration, **then** start time, each step narrowing from the one before (unlike `DAY`'s length-first order): a `DateInput` (`#reservation-pickup-date-hourly`) disabled by `isHourlyPickupDisabled` (`utils/rental.js` — closed weekday, a `closed_dates` entry, or no duration/start combination leaving even one free slot that day; for **today**, only starts not yet begun count); once a day is picked, an `OptionPicker` (radios for up to 8 options, an HDS `Select` beyond — see the component note) of `durationOptions(thing.reservation_min_minutes, thing.reservation_max_minutes)` — every multiple of the minimum up to the maximum (in **minutes** since 0150, not whole hours — an early adopter wanted reservations shorter than an hour). The named presets this list once grew — "half day" and "full day" — were **removed**: with minute-granular steps the plain multiples already say the same thing in numbers, and the cost is that a span crossing a gap between two blocks (the old "full day") is no longer offered by the UI at all — the backend still accepts one sent by start/end time, and `reservation_hour_violation`'s no-exception cap is unchanged; once a duration is picked, a second `OptionPicker` of `freeStartTimes(...)` — every start stepped by the **minimum** (so a 15-minute minimum genuinely offers quarter-hour starts, not just :00) that duration still fits **inside a single opening block**, computed from the day's own booked ranges (`dayBookings`) and, **for today, only starts not yet begun by the browser's clock** (`earliestStartMinutes`; the server refuses one too, by the deployment's clock — `DJANGO_TIME_ZONE`, the zone `opening_hours` is written in — while the picker uses the browser's; a start picked before it passed drops out of the selection on the next render and is never sent — found in review, 2026-09-18), with a `reservation.noStartTimesForDuration` fallback `Notification` when none remain (pick a shorter one) — and the same `project_note` field. A duration's label formats minutes/hours/mixed (`RequestThingPage.jsx`'s `durationOptionLabel` — `reservation.minutes`/`reservation.hours`/`reservation.hoursAndMinutes`), reusing the plain-hour key when a duration lands on a whole hour so an unchanged collection's labels don't move. Picking a new day resets both radios; picking a new duration resets the start-time one. **A Reserve click that is still missing a duration or a start time says so** (2026-09-18 — it used to do nothing visible, unlike the DAY flow's Select): the incomplete group shows HDS's `errorText` (`rental.durationRequired` / `reservation.startTimeRequired`) and focus moves to its first option, which is what a screen reader hears — see HDS accessibility bug 7. A start time is only "missing" when there were some to choose; with none, the "no start times" notice already says what to do. POSTs `{ start_date, start_time, end_time, project_note, collection_code }` — `end_time` is derived client-side (`formatHM(parseHM(start_time) + duration.minutes)`), never sent as a duration. **Once all three parts are picked, a `reservation.slotSummary` line shows the whole slot** ("Reserved on 03/06/2026, from 11:00 to 13:00.") inside the same `StatusRegion` as the "no start times" notice, so choosing a start reads it back — the end time appeared nowhere on the page before, on a reservation that auto-confirms.

    Either way, on success the notice reads *"Your reservation is confirmed"* — it is auto-confirmed, so there is no "we've let the owner know" — **and restates what and when**: the headline plus `formatRequestedWhen(body)` of the body that went out (every date-based flow, requests too).
- **Date validation**: `minDate` today, `maxDate` today + 90 days. Blocked dates fetched from calendar API. The DateInputs display **DD/MM/YYYY** (`DISPLAY_DATE_FORMAT` from `utils/rental.js`); field state holds the display string and converts to ISO at the consumption boundaries (`displayToIso` for the POST body and the derived return date, which renders back via `isoToDisplay`). When the collection offers a **single** fixed rental length, it is preselected so the pickup picker is usable straight away.
- **`formatDate(value)`** (`utils/rental.js`) — the one way the app renders a date it *displays*: `DD/MM/YYYY` for every locale (es/ca/en), matching the date pickers and `closed_dates`. Accepts an ISO date, an ISO datetime or a `Date`; `''` for anything unparseable (a null booking range shows blank, never "Invalid Date"). Replaced the bare `toLocaleDateString(i18n.language)` calls, which handed `en` readers American `MM/DD/YYYY`. Used on ThingPage (created, journey `lent_date`/`returned_date`), My/OwnerBookings (`_created`, ranges), `OwnerBookingsList`, `ThingLinkbox`, `ThingInfoRows` + RequestThingPage (`next_available`), UserPage ("member since"). Backend emails match it via `email_service._fmt_date` (see `core/services/CLAUDE.md`).
- **`formatDateTime(value)`** (`utils/rental.js`) — `formatDate` plus the local clock time: `DD/MM/YYYY HH:MM`, both parts in the **reader's own timezone** (`formatDate` deliberately drops the time an ISO datetime carries, and its datetime path renders the *local* day — so does this). The stamp a notification carries (`created`, when something happened) is the caller that needs it; `''` for anything unparseable so an absent stamp renders no line at all. Used by `InboxNotifications`' reservation meta lines.
- **`formatRequestedWhen(body)`** (`utils/rental.js`) — what a request page is about to book, read off its own POST body: an HOUR slot as `'DD/MM/YYYY, HH:MM–HH:MM'`; a DAY-unit reservation (`duration_days`) to its **last day, inclusive** — the date alone for one day — never the `start + duration` the server stores as `end_date` (the day the space is free again); a loan/rental as pickup — return. Feeds the success notice.
- **`formatBookingWhen(booking)`** (`utils/rental.js`) — a listing row's whole date/time range, reading the API's own field names (`start_date`/`end_date`/`start_time`/`end_time`) directly. A loan or rental renders `'DD/MM/YYYY — DD/MM/YYYY'`, pickup to return; a `DAY`-unit RESERVE_THING (`start_time` absent) renders to its **last day, inclusive** — the date alone for one day — since its `end_date` is `start + duration`, the day the space is free again (a one-day reservation listed as two days until 2026-09-18; `thingType` defaults to the booking's own `thing_type`, and `OwnerBookingsList` — whose calendar rows carry none — gets it from its card's `thingType` prop); an `HOUR`-unit RESERVE_THING slot renders `'DD/MM/YYYY, HH:MM–HH:MM'` — the date once, both clock times, never the day-based `end_date` (which for an hourly booking is only `start_date + 1`, the same "free again" marker the backend's calendar export and reminders read, not a real second day). `''` when there are no dates at all (GIFT/SELL). Shared by `MyBookingsPage`, `OwnerBookingsPage` and `OwnerBookingsList` — one definition so the three tables can't render an hourly slot three different ways.
- **A line above the submit button says who will see the requester's name and email**: `request.contactShared` — "Whoever runs this thing will see your name and email." (shorter than the first wording, which went on "…so they can write to you") — or, for a reservation (`isReservation`), `reservation.contactShared` ("…this space…"), a `<p class="text-muted">` that is the **first child of the final `form-grid`**, so it sits directly over the button that sends. Said before the press (DESIGN §6): the request email carries the requester's address to every manager of the thing and "Reply" reaches them, and the person should find that out here, not by being written to. **Only where that button is**: not in the join-the-group nudge (`.invite-nudge`, which shows the failed auto-join's reason and its button, with the form still below) and not in the success branch. **It does not show the address**: the page holds no user and the sentence does not earn one more request for it (the server's own emails say the same from the other side). Pinned in `test/requestContactShared.test.jsx` (a request, a reservation, directly above the button, not in the nudge, gone after the request, the three locales letter by letter); not seen in a browser.
- **Buttons**: Cancel (navigates back) + Hold / Reserve (submits request).
- On success: shows an inline HDS `Notification` ("You're all set! We've let the owner know — they'll get back to you soon.", or "Your reservation is confirmed" for RESERVE) with a "Back to {backLabel}" button. Does not navigate automatically.
- **Every verb joins on `not_a_member`**: the server asks for a place in the group for a loan, a rental, a gift and a sale as it always did for a reservation, so the page's auto-join (`joinThenRetry`) runs for any request, not only a reservation. The notice of the join is `request.joinedGroup` ("To ask here you've joined {{group}}…") for a loan or rental and `reservation.joinedGroup` for a reservation.
- On error: toast notification (top-right, auto-close), **in the reader's language when the refusal is coded**: `showRequestError` reads the body through `apiErrorMessage` (`services/api.js`), which looks a `code` up in `requestErrors.<code>` (its `params` interpolated, the number doubling as the plural count) before falling back to the server's English sentence; a 409 uses `codedErrorMessage` so an uncoded one keeps this page's own `request.dateOverlap` (every booking rule refusal is coded server-side now) — **except** RESERVE_THING's "not a member" 403, handled by `joinThenRetry`: that specific rule failure can only fire on a **PUBLIC** collection (`can_view` already gated everything else, and a non-member reaches it only there), so joining is always genuinely possible and was never really a choice being offered — the page auto-joins and silently retries the reservation, with no second click and no "you're in, try again" step in between. **Gated on the backend's `code: "not_a_member"` marker, not the bare 403 status** — `BookingRequestError.code` (`core/services/booking_service.py`), since this endpoint's *other* 403 (`get_viewable_thing`'s "not authorized to request this thing" — e.g. the thing going INACTIVE while the form was open) carries no such code and must not be mistaken for a membership gap; auto-joining on that one would silently add the reader to a group over an unrelated error. It `POST`s `/api/v1/collections/{code}/join/` — the same signed-in half of login-to-act `CollectionPage`'s `handleJoin` already uses, reused rather than reinvented. **The collection it joins is always `thing.collection_code`** — the one the server resolved the thing to (`_viewable_collection`, read through `?collection=` on the collection-context route) — **never the route's `:code` on its own** (`joinableCollection`). The route is whatever link the reader followed and nothing checks it names a collection the thing lives in: joining it as written let `/collections/<someone's PUBLIC group>/things/<a real space>/request` join the reader to that group on one Reserve click and hand its curator their email in the roster. When the route names a collection the server didn't resolve to, there is no join at all and the reason shows as a plain toast; the standalone `/things/:code/request` route has no `:code` and joins the resolved collection. **A join that happened is always said out loud**: not asking first is deliberate, but the page names the group the reader just joined and where to leave it (`reservation.joinedGroup`, "To reserve here you've joined {group}. You can leave it from your profile.") — inside the success notice when the retried reservation goes through, and in an info `Notification` of its own, in a `StatusRegion`, when it doesn't (the slot taken meanwhile): the membership stands either way, and before this nobody was told they were now in a group, its digest and its curator's roster. **A failure of the auto-join itself surfaces the rest**: a persistent `.invite-nudge` block (not a toast, which would auto-close before the reader could act) shows the backend's original reason plus a manual **"Join this group"** fallback button (`handleJoinGroup`) that retries the same join-then-reserve sequence — **rebuilding the request body fresh** (`buildReservationBody()`, shared with the normal submit path) rather than replaying the failed attempt's, since the reader may have changed the date while the fallback was showing and a stale body would confirm the wrong one. A failed retry shows its own inline error (`collectionPage.visitorJoinError`) and leaves the original reason in place. Any 403 without the marker — from either attempt — gets the plain toast.

## Shared Modules

### API Service (`src/services/api.js`)

- `apiFetch(url, options)` — Centralised fetch wrapper. Uses `credentials: 'include'` for cookie-based auth, sets `Content-Type: application/json` for requests with body. On 401: silently attempts token refresh via `POST /api/v1/auth/refresh/`. When the session is gone for good it clears `userCode` and redirects to **`loginPathFor(window.location)`** — `/login?next=<the page>` — in both places it can (refresh refused, or refresh accepted and the retry still 401; each has its own test). Only `userCode` is stored in localStorage (for ownership checks).

### Where a login returns to (`src/utils/nextPath.js`)

The refresh token lasts 7 days; after that any protected page 401s and the reader is sent to `/login`. That redirect used to forget the page, so the magic link they asked for landed on their one collection or on Home — which cut every email link (a decision notice, a question to answer, the viral "Empieza aquí", the weekly digest) off from the page it named. Now:

- **`safeNextPath(value)`** returns the value if it is a same-site path, else `''`. The rules are the server's (`core.utils.safe_next_path`, the gate — this copy is defence in depth): a string of at most 256 characters that matches `^/[A-Za-z0-9/_\-.~?=&%]*$`, does not start with `//`, has no `..` (raw or percent-decoded), is not `/` alone, and does not start at `login`, `logout`, `verify`, `rsvp` or `magic-link` (decoded, case-folded). Each side's comment names the other and `nextPath.test.js` mirrors the server's table, so they cannot drift quietly. The percent-decoding is byte-wise and never throws, because the whitelist allows a lone `%` and `decodeURIComponent` does not.
- **`loginPathFor({ pathname, search })`** is `/login?next=<encoded path+query>`, or plain `/login` when `safeNextPath` says there is nowhere to come back to. `apiFetch` and `RequireAuth` (`<Navigate to={loginPathFor(location)} replace />`) use it, and so does `JoinToAct`'s sign-in link, the hero's "Sign in" button of a public collection and the signed-out `AccountMenu` link.
- **`isDoorPath(pathname)`** — whether a path is one of the SPA's own doors: `/login`, `/logout`, `/verify/…`, `/rsvp/…`, `/magic-link/…` (decoded, case-folded, query ignored). The same list `safeNextPath` refuses, so the two cannot disagree; the signed-out `AccountMenu` paints nothing there.
- `LoginPage` reads `next` (`useSearchParams`) and sends it in the `request-link` body; the server stores it on the RSVP and `VerifyPage` follows `landing: "path"`.
- **`next` does not touch the browser's storage, on purpose.** The magic link is often opened in another browser (Gmail's web view, the phone's mail app), which shares nothing with the one that showed `/login`; the server-side RSVP is what crosses that gap. It also leaves the README's inventory of storage keys, which `browserStorage.test.jsx` guards, exactly as it was.

### File downloads (`src/utils/downloadBlob.js`)

`downloadBlob(blob, filename)` — hands an already-fetched `Blob` to the browser as a download. There is no declarative way to do it (a `<a download>` needs a URL that exists only after the response), so it is a dozen lines of imperative DOM, and both ways a copy of them drifts are invisible in the happy path: an object URL that is never revoked pins the blob in memory for the life of the tab, and an anchor left in the body is a stray focusable element between the page's real controls. **The caller keeps the request and its failure copy** — what a 429 should say differs per page, and this function never sees the response. Used by `useCollectionDownloads` (the stats CSV and the collection export), `useCalendarExport` (the calendar), `DataExportPage` and anything else that offers a file.

`filenameFromResponse(res, fallback)` — reads the `Content-Disposition` filename off a response, or `fallback` if it's missing. Shared so the two data-export downloads (`DataExportPage`, and the collection menu's JSON export through `useCollectionDownloads`) read the server-set `oiueei-{code}-{date}.json` name identically rather than each guessing their own — the stats CSV still builds its own name client-side (`{code}-stats.csv`), since that endpoint never set the header.

### Owner content in one text per language (`src/utils/localized.js`)

The mirror of `core/utils.py::parse_localized` / `resolve_localized` — and it must **stay** a mirror: if the two sides disagreed on what counts as a map, a card would show raw braces for content whose email reads as words. `parseLocalized(value)` returns the `{lang: text}` map or `null` (strict: a JSON object, keys ⊆ `es`/`ca`/`en`, all values non-empty strings — everything else is prose and renders verbatim). `localizedText(value, lang)` resolves it (`lang` → `es` → the first language written, so nobody ever faces JSON), and **`useLocalized()`** binds it to the reader's language — the frontend twin of the email service's `L`:

```jsx
const L = useLocalized();
<h1>{L(thing.headline)}</h1>
```

Every site that renders owner content calls it: `ThingLinkbox`, `ThingPage`, `CollectionLinkbox`, `CollectionPage` (which resolves once and hands the words to its children — cards, share menu, back labels, **and its own tag-filter bar chips**: the raw string stays the filter key — `includes`, `effectiveTag ===`, the React `key` — only the chip label resolves), `HomePage` (inbox payloads + pending invitations), `MyBookingsPage`, `OwnerBookingsList`, `RequestThingPage`, the delete/leave confirms, `ThingTags` and the tag pickers, plus every `document.title`. The **edit forms are the exception**: they show the *raw* value, because that is what the owner is editing — only their title and back label resolve. `localizedCounter(value, limit)` is the form counter: `18/64` for plain text, `es 18/64 · ca 17/64` for a map (each language gets the whole limit — the rule the server enforces), plus an `over` flag the forms turn into an inline error.

### Custom Hooks

- **`useThingBooking`** (`src/hooks/useThingBooking.js`) — The lower-level booking **engine**: owns the reservation state, the owner-calendar fetch (`AbortController`-guarded, re-runs by `thing.code`), and the three async handlers (`handleRequest`, `handleActivate`, `handleBookingAction`). **A `403` on accept/reject is its own message:** the server refusing a decision means this reader no longer runs the thing — a co-curator demoted in another tab whose card still offers "Confirm hold / Decline hold" — so `handleBookingAction` says `thingPage.noLongerDecides` ("You can no longer decide this request. We've reloaded it…") and **reloads the thing** (`GET /things/{code}/`, through the collection when there is one) into the parent via `onThingChange`, so the controls that are no longer theirs disappear; if the reload fails the generic `errorConfirmingHold`/`errorCancellingHold` stands ("reloaded" would be untrue), and every other status is as before. Both `ThingLinkbox` and `ThingPage` get it, as both go through this hook. The card-vs-page differences are options (`initialActivePending`, `initialRequested`, `fetchOnEndless`, `bookingKeepsStatus`, `activateSuccessMessage`). **`collectionCode`** is sent in the request POST body: a thing can live in several collections, and the one the requester was browsing is what decides where the owner's notification appears — `ThingLinkbox` passes its `collectionCode` (or `thing.collection_code`), `ThingPage` the same code it uses for login-to-act; the standalone `/things/:code` page has none and the backend falls back to its own approximation. `RequestThingPage` (dates) already posted it for the rental rules. Returns `{ submitting, requested, bookingAction, bookingActionVerb, activating, bookings, activePendingCode, handleRequest, handleActivate, handleBookingAction }`.
- **`useThingActions`** (`src/hooks/useThingActions.js`) — The **view-model** layer wrapping `useThingBooking`, shared by `ThingLinkbox` and `ThingPage` so the owner-button-matrix / reserve-button logic lives in one place. Derives the type flags (`isOwner`, **`canManage`** — `thing.can_manage`, floor `isOwner`; the matrix, `canDelete` and the `!canManage` reserve-button guard all key on it now — `isCollectionOwner`, `isDateBased`, `needsPage`, `canDelete`, `hasPendingBookings`) and the reserve button's `showButton` / `buttonDisabled` / `loginButtonDisabled` / `buttonLabel` — plus everything `useThingBooking` returns. `canManage` is also what it passes `useThingBooking` to gate the owner-calendar fetch (the backend serves the requester-detail calendar + embedded `bookings` to a manager, not only the owner). The genuine differences are options: `isPaused` (card on a paused collection; the page passes false), `canAct` (the page passes `isAuthenticated`), `loginToAct` (anonymous-on-public — buttons show but each click routes to `/collections/:code/join`), `collectionOwner`, `collectionCode` (forwarded to `useThingBooking`, above), and the `useThingBooking` seeds. `bookingKeepsStatus` (`needsPage || is_endless`) is derived here so callers don't repeat it. Signature: `useThingActions(thing, userCode, options)`.
- **`useCapabilities`** (`src/hooks/useCapabilities.js`) — What this deployment lets the signed-in account create: the `capabilities` block on `GET /auth/me/` (`{collection_modes, thing_types, request_url}` — see `core/services/CLAUDE.md`). One request per signed-in account, shared by every form that asks and keyed by `userCode` so it cannot outlive a logout. **Null until known and null on failure**, and every caller reads null as "no restriction" and offers the whole catalogue: this is a courtesy to the user, never the gate — the gate is the server, which refuses regardless of what the browser managed to fetch. **A failure is not cached** (a non-OK status counts as one): failing open is deliberate, remembering the failure was not, since one offline blip would otherwise keep every later form in that session offering what the deployment refuses, ending in a 403 nobody could have predicted. An answer *without* the field does cache — that is a real answer, meaning no restrictions. Contract pinned in `test/capabilities.test.jsx`. `isOfferable(capabilities, kind, value, current)` is the predicate the four forms filter their options with; `current` (the value being edited) is **always** offered even when the policy no longer allows it, mirroring the server, which only judges a *change* — a form that hid the current answer would display one thing and submit another. The module's cached `/auth/me/` fetch (`loadMe`, private) is also what **`loadUserLanguage`** (exported alongside `loadCapabilities`) reads — the account's own deliberately-saved `language`, or `''` for signed-out/no-preference/failure, same fail-open shape. It exists for `useCollectionLanguage` below, and shares the one request rather than opening a second. **Checks `localStorage.getItem('userCode')` before ever calling `loadMe()`, and asks it with `optionalAuth: true`** — every pre-existing caller of the shared cache (`loadCapabilities`) only ran from a page already behind `RequireAuth`, so `apiFetch`'s 401→refresh→redirect-to-`/login` never fired for a signed-out visitor in practice; `useCollectionLanguage` is the first caller reached from genuinely public pages, and without the `userCode` guard, opening any of them for a collection with a `language` set would silently hard-navigate every anonymous visitor to `/login` (found in review, 2026-09-15). The `userCode` check alone still missed one case, found in a second review pass the same day: `userCode` never expires on its own, but the cookies behind it do (`access_token` 1h, `refresh_token` 7d) — a visitor who signed in over a week ago still has `userCode`, so `loadMe()` still 401'd and still redirected. `optionalAuth: true` closes that for good: a failed request comes back as a response to inspect, never a redirect — and `loadMe()` now clears `userCode` itself on a definitive 401 (never on a non-401 failure), so the next protected page's `RequireAuth` still catches a dead session honestly instead of repeating the failed refresh forever (a real cost against `/auth/refresh/`'s 10/minute-per-IP limit). **`loadCapabilities` asks strictly, `loadUserLanguage` optionally** (fixed 2026-09-18): the pages that consume capabilities sit behind `RequireAuth`, and on `CreateCollectionPage` it is the only authenticated call before submit — while the shared fetch was `optionalAuth` for everyone, a >7-day-stale session there rendered the form and lost whatever was typed at the POST (found in a third review pass, 2026-09-15). Each caller now states its mode; a strict caller shares a strict or a successful request, and after an optional one's failure asks again strictly, which is what lets `apiFetch` redirect. Pinned in `test/capabilities.test.jsx` ("a dead session: who redirects and who does not"). **`invalidateMe()`** drops the shared cache outright — `EditProfilePage`'s save handler calls it on success, since that page changes `language` but neither reads nor updates this module's cache; without it, a member who opened a collection (caching the pre-edit language) and then changed their profile language would see the stale value again on their very next visit to any collection, until a full reload.
- **`useJoin`** (`src/hooks/useJoin.js`) — The shared `/auth/join/` submit behind the email-capture doors: `MagicLinkJoinPage` (`/share/:token`, plus any a deployment adds) and `JoinToAct` (inside `JoinPage`). They stay separate components because they render very differently — boxed page vs unboxed hero body with inline errors — but the request was byte-identical in both and had already drifted. Owns `email` / `loading` / `status` / `message` plus the CSRF header, the 429 branch, and a **ref-based** re-entry guard — a `loading`-state guard is useless against a second submit in the same tick, which runs the previous render's closure and still sees `false`. **Never sends a `language` field** — it used to, so a brand-new member's first magic link would speak the page's current UI language, but the backend stamped that value onto the new user permanently, and it then outranked the joined collection's own language for every future email to them, with no way back short of a profile edit. The backend resolves the first magic link from the collection instead — one fewer thing for this hook to send. Options: `sentMessageKey` / `errorMessageKey` (the copy differs per door) and `extraBody` (`JoinToAct`'s `collection_code` plus an optional `thing_code` from the `?thing=` query param, `SharePage`'s `share_token`). - **`useCollectionLanguage`** (`src/hooks/useCollectionLanguage.js`) — Applies a collection's own `language` to a page's **generic UI chrome** (`anonIntro`/`anonIntroLink` — "This group shares its things on OIUEEI. Join to take part →", since removed from the hero (2026-09-21) — `joinToAct.heading`, and every other plain i18n string on that page); (the symptom was exactly that English line on a Catalan collection). **It moves owner content too** — owner text resolves by the reader's current language (`useLocalized`), not per collection as this note first claimed — so **the owner's own translations veto it**: each page passes the raw owner texts it shows as `ownerTexts` (a headline, a description), and when one is a `{lang: text}` map holding the reader's language, nothing is overridden. Before that, on a Catalan-language group whose owner had written every headline in Spanish too, a Spanish browser with no saved preference — every anonymous visitor, every member who never touched the profile Select — was shown the Catalan, with no language control short of an account. What the hook still does is the case it was written for: text written once, in the collection's language, framed by chrome in the browser's. The edit pages pass the texts **as loaded/saved**, never the live draft, so typing cannot flip the form's language. Hierarchy: a signed-in visitor's own deliberately-saved language always wins; failing that, `collectionLanguage`; failing that, today's plain browser/localStorage default, untouched. **This hook only ever implements the middle tier** — given that a real preference exists (`loadUserLanguage`, above), it stays out of the way; *applying* one for real, on a device where it isn't already the cached default, is `App.jsx`'s own `/auth/me/` warm-up effect, which runs once per visit ahead of any page (added 2026-09-15 in review — without it, a preference saved on one device did nothing on another, since nothing but `EditProfilePage`'s own Select ever called `changeLanguage` with it). **The one rule that makes this hook's own override safe**: it never writes into the `i18nextLng` cache `i18next-browser-languagedetector` reads back on the *next* boot — doing that would silently stamp a fresh visitor's first collection as their permanent browser default everywhere else too, the exact frontend twin of the `JoinView` bug just fixed server-side. Every `changeLanguage()` call it makes (applying the override on mount, reverting it on unmount/prop change) is followed **synchronously** by restoring the cache entry to whatever it found — not chained onto the returned promise, since `i18next`'s cache write happens synchronously inside `changeLanguage`, before that promise resolves; for `es`/`ca` that promise waits on a lazy-loaded chunk, and restoring only in `.then()` left the wrong value cached for the whole download (found in review, 2026-09-15). Takes the raw `language`/`collection_language` string from a `Collection`/`Thing`/`SharePreviewView` response (`''`/`null`/unsupported = no-op) and returns nothing — it's an effect, not a value. ### What this deployment adds (`src/deployment/`)

The frontend half of the backend's `DEPLOYMENT_URLCONFS` / `CREATOR_POLICY` extension points. **Upstream exports nothing but empties** — the app renders exactly as it did before the indirection existed. A deployment with pages of its own **replaces the whole directory** instead of editing `App.jsx`, `LoginPage.jsx`, `SiteFooter.jsx` or the locale files: those are files upstream keeps changing, and editing them buys a merge conflict on every update, while a directory it owns outright has none. (The same trick already worked by accident for `src/legal/{lang}.js`; here it is deliberate.)

| Export | Consumed by | Meaning |
|---|---|---|
| `deploymentRoutes` | `App.jsx` | `[{path, Component}]`, `Component` usually `lazy(() => import(...))` like every other route. Mounted **above** `path="*"` — a route declared after the catch-all renders the 404 page instead, and nothing else about the app looks wrong |
| `popInPath` | `LoginPage` | Where the "new here?" button goes, or `null` for **no button at all** — the honest answer upstream, where the only ways in are an invitation and a share link |
| `aboutPath` | `SiteFooter`, `HomePage` | A page saying what this deployment *is*, or `null` for none. Null upstream: what OIUEEI is belongs in the README, and an operator's own pitch belongs to the operator. It decides the footer's about link and the dashboard empty state's second button (it also decided where `landing: "welcome"` sent a new visitor until 2026-10-04, when that landing was removed) |
| `faqPath` | `LoginPage` | Where this deployment's help/FAQ page lives, or `null` for none. Linked from `/login`, the door with the most traffic — a FAQ answers questions about a *particular* deployment (who operates it, what it lets people create, how to ask for something it holds back), so it has no home upstream. Rendered at the foot of the page as a full-width secondary button (the same shape as "New here?" above), with nothing after it since 2026-10-04 (with the other deliberate-lookup links, not floating above the reading; the "trouble signing in?" line that used to follow went to the footer's "Contact us"), same `null`-means-no-link shape as `aboutPath` |

## Internationalisation (i18n)

All UI strings are externalised via `react-i18next`. No hardcoded strings in components.

- **Setup:** `src/i18n/index.js` initialises i18next with `i18next-browser-languagedetector` (detection order `localStorage` → `navigator`, the chosen language cached in `localStorage`), falling back per `fallbackLng` for unsupported languages. **English (the fallback) is bundled eagerly** in `resources` so the first paint is always translated; Spanish and Catalan load on demand through a tiny custom i18next backend (`partialBundledLanguages: true`, `load: 'currentOnly'`) — see Locale files.
- **Supported languages:** English (`en`), Spanish (`es`), Catalan (`ca`).
- **Retired languages:** Brazilian Portuguese (`pt-BR`), European Portuguese (`pt-PT`), Basque (`eu`), and Galician (`gl`) were dropped from `supportedLngs`/`resources` 2026-07 (paused, not deleted — the locale JSONs are recoverable from git history). `fallbackLng` is an object mapping each retired code (plus bare `pt`) to `['es']`, with `default: ['en']` for any other unsupported browser language.
- **Locale files:** `src/i18n/locales/{lang}.json` — one JSON file per language with ~690 keys organised by namespace (common, titles, login, verify, home, collectionPage, thingPage, types, availability, condition, etc.). Only `en.json` ships in the main bundle; `es.json`/`ca.json` (~35 kB each) are **code-split into their own Vite chunks** via the backend's `import()` of the locale JSON and fetched only when that language is active (a non-English visitor briefly sees English before the chunk lands — `react: { useSuspense: false }`, so no spinner).
- **`html[lang]`:** updated dynamically in `App.jsx` via `i18n.on('languageChanged', ...)` — but that runs after React mounts, so the very first paint (and every crawler) used to see the static `lang="en"` in `index.html` regardless of the visitor's actual language. `public/detect-lang.js` closes that gap: a synchronous, dependency-free script loaded via `<script src="/detect-lang.js">` (an **external** file — CSP's `script-src 'self'` has no `'unsafe-inline'` in production, `core/middleware.py`, so an inline block would be silently dropped) that mirrors `i18next-browser-languagedetector`'s own priority (saved `i18nextLng` in `localStorage`, then `navigator.languages`) and `src/i18n/index.js`'s `fallbackLng` map, so it never disagrees with what i18next settles on once it loads. Tested by sandbox-evaluating the real file's source (`src/test/detectLang.test.js`), since it can import nothing a browser wouldn't have yet.
- **Usage:** every page and component imports `useTranslation` and calls `t('namespace.key')`. Select options are built inline: `TYPE_VALUES.map(v => ({ label: t('types.' + v), value: v }))`.
- **Initialisation:** `import './i18n'` in `App.jsx` (before HDS imports).
- **Nouns** (settled on 2026-09-19), for any new copy:
  - **What a collection holds is a "cosa / cosa / thing"**, never "artículo / article" (the two had ended up on the same screen). No "espacio / espai / space", "local" or "sala" for what a reservations collection offers either — it can be machinery, a resource or an expert's time: leave the noun out where the sentence allows ("¿Cómo se reserva?", "Un miembro puede reservar de 1 a N días"), and say "cosa" where one is needed.
  - **es/ca: "solicitud / sol·licitud" is a pending request** (a hold on a gift, sale, loan or rental, which the owner confirms or declines) and **"reserva" is only RESERVE_THING**, which confirms on the spot. The two used to share "reserva" — "Confirmar reserva" on a loan card, "Reserva confirmada" in the inbox for a hold — while English already said *hold/request* vs *reservation*. The generic verb for acting on a card is "pedir / demanar"; where a sentence covers both, it names both ("solicitudes y reservas").
  - English "Proprietary" and "Lend" stay as they are (D4/D5, declined).
  - **The door for someone with no account says "Join", not "Sign in"** (`joinToAct.body` — generic, until the collection has loaded — and `joinToAct.bodyActions`, 2026-09-29 / 2026-10-02: en "Join to claim, buy, borrow, rent, and add your own things in X", es "Únete para tomar prestado y añadir tus propias cosas en X", ca "Uneix-te per reservar a X"; the verbs are the collection's own, `utils/joinActions.js`: the thing types it allows in the cards' order — none listed means the four lending-and-giving types — plus "add your own things" only in a COMMUNITY one, joined by the language's conjunction; "ask" is not promised): `JoinPage`'s title is "Join to take part", and the person there typed an address to *create* the account, so "Sign in" promised something they don't have. `login.pitch` in es says "pedirlas", the generic verb, not "encargarlas".
  - **A Proprietary group is not "only you"**: since co-curators, `createCollection.modeProprietaryDesc` says "Only the team running the group adds things — you, to start with." — true even where a deployment turns co-curators off (`co_owners_enabled`).

## Testing

Smoke tests and automated accessibility checks using vitest + testing-library + jest-axe.

- **Run tests:** `npm test` (single run) or `npm run test:watch` (watch mode).
- **Config:** `vite.config.js` — `test` block with jsdom environment, `src/test/setup.js` as setup file.
- **Setup:** `src/test/setup.js` — imports `@testing-library/jest-dom`, initialises i18n mock, provides `localStorage`, `CSS.supports`, and `ResizeObserver` polyfills for jsdom.
- **Smoke tests:** `src/test/smoke.test.jsx` — renders every page component with mocked API responses and runs `jest-axe` to detect WCAG violations. Covers all 29 page components.
- **i18n mock:** `src/test/i18n-mock.js` — initialises i18next with the real `en.json` for test rendering.
- **Slow form-page tests: `dropHdsStyles()` (`src/test/dropHdsStyles.js`, 2026-09-29).** `hds-react` injects ~75 `<style>` sheets (~350 kB, ~1,700 rules) into `<head>` *when it is imported* — `css: false` does not reach them — and jsdom's `getComputedStyle` walks every rule for every element it is asked about, which `getByRole(…, { name })` does for each candidate to compute an accessible name. Measured on `EditCollectionPage` (429 elements, 32 buttons): a name query right after a DOM change cost **450–650 ms** (40 ms without the sheets), and 55 of them were **90 %** of the file's test time (20.8 s of 23 s; `collectionForm.test.jsx` 12.9 s of 16.3 s). That, not typing or mounting, is what brushed the 20 s `testTimeout` under coverage on a loaded machine. `beforeEach(dropHdsStyles)` in those two files took them from 24 s → 4.5 s and 17 s → 3.4 s alone (slowest test 1.7 s → 0.17 s, the axe test 2.4 s → 0.29 s) with every behaviour intact — a folding `Accordion` still reads `not.toBeVisible()` without the sheets, because it hides with `hidden`/inline `display`, not a class rule; and mutating the behaviours the files assert still fails them. Vitest gives each file its own document, so nothing leaks. **Use it only where a test asserts behaviour**, not one whose point is what a stylesheet does; the other slow files (any that render many HDS components and query by role) would gain the same, which is a decision for each, not a global switch. `testTimeout` was not raised.
- **The hourly grid is pinned on both sides of the wire:** `src/test/hourlyGridParity.json` is a table of cases — opening blocks, the minimum-minute step, bookings, the clock — with the start times each should produce. `src/utils/hourlyGridParity.test.js` runs `freeStartTimes` / `isHourlyPickupDisabled` over it, and `core/tests/unit/test_hourly_grid_parity.py` puts every start of a five-minute sweep to `Collection.reservation_hour_violation` + `has_overlap`; both must produce exactly the listed starts. Tested apart, the page could offer a start the server refuses (or grey out a day with room) with both suites green. Add a case to the JSON rather than to either test, and keep its `note` — that is where the expected starts are derived by hand, so neither side is copying the other's output. The one deliberate divergence: the server still accepts a full-day span across a gap, which the picker stopped offering in 2026-09, so no case uses one.
- **Linting:** `eslint.config.js` runs `jsx-a11y.flatConfigs.strict`, not `recommended` — matching the ratchet culture elsewhere in this repo (coverage, dependency audit): a stricter floor than the framework default, checked automatically rather than hoped for. Switching it turned up exactly two findings, both `no-static-element-interactions` on the same deliberate idiom: `InfoPopover` and `TooltipButton` wrap a real, fully keyboard-accessible HDS `Button`/`<button>` in a plain `<span>`/`<div>` that only listens for the child's focus/blur bubbling up, to control a hover/focus-revealed panel's visibility. The wrapper is never itself a keyboard target, so the rule's fix (give it a role and full keyboard support) would be solving a problem that isn't there; both carry a scoped `eslint-disable-next-line` immediately above the tag, with the reasoning inline rather than silent.

### The dependency audit gate (`scripts/audit-gate.mjs`)

CI runs `node scripts/audit-gate.mjs` instead of `npm audit --audit-level=high`. Same threshold — it fails on any high or critical advisory — but it can accept a named one, which plain `npm audit` cannot. Without that, a single unfixable finding leaves only two options: a permanently red pipeline, or dropping the whole gate to `critical` and silently ceasing to guard every other high.

An allowlist entry requires **both** conditions, written into the script next to the id: the advisory has **no published fix**, and its vulnerable path **cannot be reached from this app**. It also records what would let it be deleted. A high with a fix we simply haven't applied must never be listed. The script also flags an entry that no longer matches anything (fixed or withdrawn upstream) so the list doesn't rot — as a message, not a failure, since a greener audit must not turn the build red.

The decision is a pure function (`evaluateAudit(report, allowlist)`); running npm, printing and exiting sit around it, and importing the module runs nothing. That split exists so `scripts/audit-gate.test.js` can exercise the gate itself — a gate nobody tests can quietly stop guarding, and the failure looks exactly like a green build. The suite pins what blocks (unlisted high/critical), what doesn't (moderate/low, listed entries), that listing one advisory never stops the others blocking, that a stale entry is reported but never fails the build, that `npm audit`'s non-zero exit on findings is normal while a scanner that **couldn't run** is fatal, and that every real allowlist entry carries all three justifications.

**Currently allowed: nothing** — `ALLOWED` is `{}`, and that is the state to keep it in. The only entry it ever held was **GHSA-qwww-vcr4-c8h2** (react-router RSC-mode CSRF), accepted because the fix, react-router `8.3.0`, was unpublished and npm's only suggestion was a downgrade to 7.11.0 that reintroduced four advisories 7.18.2 had fixed. 8.3.0 shipped, so the debt was paid the way an allowlist entry is meant to be — by taking the upgrade and deleting the entry, not by re-justifying it. When the list is empty, `every real entry justifies itself on both counts` iterates nothing, so a companion test pins the bar itself against entries that must fail it; keep that pairing if you ever add an entry back.

### HDS Select quirks

Every `<Select>` must say which language HDS should speak, because its own
assistive wording ("choose one", "2 selected options", "clear current
selection") defaults to **Finnish**. In HDS 5 that was the `language="en"` prop,
and this file said so for a year. **HDS 6 moved it inside `texts`** —
`texts={{ label: …, language: 'en' }}` — and ignores the prop silently: the
component still renders, the page still looks right, and the only thing that
changes is what a screen reader reads out. Fourteen Selects spent the HDS 6
upgrade announcing themselves in Finnish, and no axe rule catches it (none
compares the language of an `aria-label` against the page's). `src/test/
selectLanguage.test.jsx` now renders one such form *and* sweeps the source for
the dead prop, since the failure is invisible on screen.

`'en'` is the honest value everywhere: HDS ships fi/sv/en, and none of this
product's three locales is among the other two.

`DateInput` and `Accordion` do honour a `language` prop — verified, not assumed —
and every call site passes `hdsLang(i18n.language)` (which is `'en'` for es/ca/en,
since HDS ships only fi/sv/en; `8b41f36` routed the last seven literals through it). `DateInput`'s `language` only reaches fi/sv/en, so
its calendar's **month and weekday names stay English** for an es/ca reader
(HDS bundles only those three date-fns locales, hard-keyed off the prop — there
is no seam to inject a fourth). What *is* reachable are three label props, and
`RequestThingPage`'s four `DateInput`s now pass them from i18n
(`datePicker.open` / `.select` / `.close` → `openButtonAriaLabel` /
`selectButtonLabel` / `closeButtonLabel`); `dateOutsideRangeErrorText` /
`malformedDateErrorText` were already localised. Full es/ca months/weekdays
would mean replacing the calendar itself — deferred, and if done it goes in
both editions, not hosted-only. `RequestThingPage.test.jsx` pins the wiring.

Additional API notes: `value` is an array of the selected **option objects**
(`[{ label, value }]`), `onChange` receives an array (`(sel) => sel[0].value`),
error text uses the `error` prop (string), not `errorText`. The `icon` prop
renders inside the one `<button role="combobox">`, before the placeholder text.
**Handed a bare string it cannot resolve against `options`, the combobox
renders that string verbatim** — this is how a raw `GIFT_THING` reached the
`ThingForm` type box (2026-09): `value={type}` where `type` was the default and
the collection's allowlist did not offer it. Always pass
`options.filter(o => o.value === current)`, never the raw value —
`AddThingPage.test.jsx` pins the type box against its own code showing.

**`ShareCollectionMenu` restyles a Select trigger to a bare icon** (`.share-corner`,
App.css) — the only place this app does that. It leans on HDS's internal
CSS-module class *prefixes* (`Select-module_root`, `selectAndListContainer`,
`listAndInputContainer`, `FieldLabel-module_label`) via `[class*='…']`, since the
hashed suffixes change between builds. Behaviour is pinned by
`ShareCollectionMenu.test.jsx` (one named combobox, menu opens with every
option), but the *look* is not testable in jsdom — on any `hds-react` bump,
re-check the collection hero by eye: a 44px icon, no border/box, and the options
list opening at a readable width anchored to the icon's right edge.

### HDS ToggleButton quirks (v5)

Four non-obvious behaviours:

1. **`onChange` receives the current value, not the new one.** Always negate: `onChange={(val) => setState(!val)}`.
2. **`style` prop targets the inner `<button>`, not the flex container.** Flex layout overrides via `style` have no effect. Use `<div className="toggle-left">` wrapper instead — the `.toggle-left` CSS class in `App.css` reverses the flex direction to put the pill on the left.
3. **`disabled + checked` renders light grey by default.** Overridden to `--color-black-90` in `App.css` via `.toggle-left button[aria-pressed="true"][disabled]`.
4. **Multi-line labels (title + `<br/>` + long helper) wrap the pill onto a new row.** HDS's inline container allows wrap by default; a long helper makes the label wider than the available row and the pill drops below. Fixed in `.toggle-left` with `flex-wrap: nowrap; align-items: flex-start` on the container plus `flex-shrink: 0` on the inner button.

### Links — three kinds, and why HDS `Link` is not used yet

> Superseded in part by **A link that looks like a button** below: keyboard
> testing found a fourth kind this list missed — a router `Link` wrapped
> around an HDS `Button`, 25 of them — and they are now `ButtonLink`, built on HDS's
> own `Link`. So this app does import HDS `Link` after all, just not yet for kind 3
> (external links), where the reasoning below still stands.

HDS ships a `Link` component and this app imports it **nowhere**, which under DESIGN §1 needs a reason rather than a silence. Reviewed 2026-08-17; the reason is that "link" here means three different things:

1. **Internal navigation** — react-router's `Link`, and it has to be: an HDS `<a>` would reload the SPA. This is the overwhelming majority, and it is not a deviation at all (HDS has no router).
2. **Generated HTML** — `MarkdownText` builds `<a href=…>` as a **string** and injects it. A React component cannot go there without rewriting the whole renderer, and that renderer is where the escaping invariant lives (see `MarkdownText`). Off the table.
3. **External links in JSX** — 5 sites (`ApprovalNotice`, `PdfUpload`, `LoginPage` ×2, `EditProfilePage`; `FeedbackLink` was the sixth until 2026-10-03, when it became an HDS `Link` button — and found that `openInNewTab` prints its label), all `<a target="_blank" rel="noopener noreferrer">`. **This is the one HDS `Link` should own**, and the one place it would add something real: `external` + `openInNewTab` render the outbound icon and announce the new tab, which none of the six do today.

What has kept (3) from happening is not the component, it is that it is a **copy change in three languages**: HDS's `openInNewTabLabel` defaults to Finnish (`"(avautuu uudessa välilehdessä)"`, the same trap as `Select`'s `language="fi"`), so adopting it means three new i18n keys ×3 locales plus a visible label and icon appearing next to six links — including two inside `<Trans>` placeholders. That is a design decision with visible consequences, not a refactor, so it belongs to a design pass with someone looking at it, not to a pre-release cleanup.

### HDS SelectionGroup quirks

Two, and the first one fails **silently** — both learned the expensive way while replacing the hand-rolled `<fieldset>` in `CollectionModeField`:

1. **It does not flatten its children.** `{options.map(...)}` arrives as a single child that *is* an array, `isValidElement` rejects it, and the whole group renders empty — a fieldset with a legend and no radios, no error anywhere. Pass one flat array instead: `{[...optionFields, <Extra key="…" />]}`.
2. **It re-wraps every child in a `<div key={child.props.id}>`.** A child without an `id` prop gets `key: undefined`, so React logs a missing-key error for each one. Children that are wrappers rather than HDS controls therefore carry an `id` they have no other use for.
3. **That wrapper `id` must NOT be the same string as the `RadioButton`'s own `id`.** Give it a distinct one (`CollectionModeField` and `RadioOptionGroup` both use `${id}-option`) — reusing the radio's own `id` on the wrapper `<div>` puts two elements in the DOM sharing one `id`, and `<label for="…">` then resolves to whichever one it finds first (the empty wrapper), so **every radio's accessible name goes blank** — this passes a bare radio-count assertion (`getAllByRole('radio')` still finds them) and only fails a name-scoped query (`getByRole('radio', { name: … })`), which is exactly why the plan for this feature called for a radio-count test in the first place and why that alone would not have been enough on its own.

It also owns the vertical rhythm (`--spacing-row`, a grid `gap`), so per-option margins are its job, not the caller's.

### HDS accessibility bugs we carry

Found by keyboard testing on **2026-08-30**, all in `hds-react@6.0.5`, all verified
against the shipped bundle rather than the docs. The decision each time was the
same and it is deliberate: **stay on HDS, work around it only where the workaround
is itself an HDS API, and wait for upstream on the rest.** Delete an entry here
when a release fixes it — do not let one rot into a permanent local fork.

**1. `Linkbox` announces as a region, not a link.** It renders
`<div role="region" tabindex="0">` with the real `<a>` inside at `tabindex="-1"`,
and activates it from an `onKeyPress` handler. So the card *is* reachable (one tab
stop) and Enter *does* follow it — but it is announced as "region", it never appears
in a screen reader's list of links, **Space does not activate it**, and `onKeyPress`
is a deprecated React alias. HDS's own documentation site renders the identical
markup, so this is theirs, not a misuse. **Not worked around** — the only fix is to
stop using the component, which costs more than the defect. Affects the collection
grids on `HomePage` and `UserPage` (`CollectionLinkbox`).

**2. A deletable `Tag` has no name for what it does.** v6 makes the *whole chip* the
control — one `<div role="button">` named from its own text — and there is no
`deleteButtonAriaLabel` prop any more. A screen reader announces "button, Vintage"
and nothing about removal. **Worked around**: `TagInput` passes its own `aria-label`
(the rest props land on that div, last in the `Object.assign`, so it wins). Pinned by
`TagInput.test.jsx`.

**3. Nine components hard-code their focus ring to `var(--color-coat-of-arms)`**
instead of reading `--color-focus-outline` the way the rest of HDS does —
`DatePicker` days, `DialogHeader`'s close and title, `Linkbox`, `Notification`'s
label, `Table`'s sort button, `ToggleButton`. They also set `outline: none` and draw
their own `box-shadow`, at a specificity a global rule cannot reach, so the two-tone
ring in `App.css` does not apply to them. See the focus-ring comment there for why a
single colour fails; `#0072c6` clears 3:1 on only 31 of the 48 theeeme surfaces.

**4. Icons carry no `aria-hidden`.** `IconFoo` renders a bare decorative `<svg>`, so
**every** call site has to add `aria-hidden="true"` itself (or a label, when the icon
is the only content). There is no default and no lint rule; the audit found two that
had been missed.

**5. An inline `Notification` is announced by nobody.** It gets `role="alert"`
**only** when it is positioned — a toast. Inline, it gets no role at all, so of the
42 in this app exactly one was ever announced: press Save, have it fail, and a
screen reader said nothing. That is WCAG 4.1.3 Status Messages, level AA. The role
cannot be supplied from outside either — HDS spreads rest props *before* its own
`role: … : void 0`, so passing one is erased. **Worked around** two ways, by shape:
a message that is *appended* to the page goes inside `StatusRegion`, a live region
that renders unconditionally so it pre-dates its own content; a message that
*replaces* the form gets HDS's `autofocus`, which both rescues the focus the
vanished submit button was holding and gets the message read. A load error that
*is* the page needs neither — it is read in document order.

**6. `Link`'s new-tab and external-domain labels default to Finnish**
(`"avautuu uudessa välilehdessä"`, `"Siirtyy toiseen sivustoon."`) — the same trap as
`Select`'s `language`, and just as invisible, since it only changes what is announced.
Any adoption of `Link` with `openInNewTab` or `external` **must** pass
`openInNewTabLabel` / `openInExternalDomainAriaLabel` in all three locales.

**7. A `SelectionGroup`'s `errorText` is linked to nothing.** It renders a plain `<div>`
after the options — no `id`, no `aria-describedby` from the fieldset or its inputs, no live
region — so it is visible but never announced (verified in `hds-react@6.0.5`'s bundle, 2026-09-18).
**Worked around** where it matters: `RequestThingPage` moves focus to the first option of the
group it flags on a failed Reserve, so the question is read out; the text stays HDS's.

### A link that looks like a button: `ButtonLink`

`Button` always renders `<button>` — there is no `as` or `href` prop, and wrapping it
in a router `<Link>` produces nested interactive elements: **two tab stops for one
control**, announced "link… button", with the `<a>` taking the focus ring while the
`<button>` carries the look. `jsx-a11y` has no rule for it and **axe reports no
violation**, which is how 28 of them accumulated.

HDS's own answer is `Link`'s `useButtonStyles`, which swaps the link class for
`hds-button hds-button--primary` — the real button CSS, same `--computed-*` token
chain. `src/components/ButtonLink.jsx` wraps it, and **25 call sites across 11 files
now use it**:

```jsx
<ButtonLink to={editPath} fullWidth style={btnSecondaryStyle}>{t('common.edit')}</ButtonLink>
```

Three things about it are load-bearing:

- **There is no `variant` prop.** What makes a button secondary here is the token
  set (`btnSecondaryStyle`), not HDS's variant class, so the same element serves
  both. HDS's own `hds-button--secondary` is a hashed CSS-module name we could not
  address even if we wanted it.
- **`fullWidth` is ours** (`.button-link--full`, one declaration) — `Link` has no
  such prop, and the base class already centres the label.
- **The `<a>` it renders IS the button** — `hds-button--primary`'s background,
  border and padding sit on the `<a>` itself, with a `<span>` inside for the
  label. So a rule that removes the `<a>`'s box (`display: contents`, `display:
  none`) paints none of that and drops it out of the a11y tree. This bit the
  card grid: `.thing-card-buttons a { display: contents }` was added in 2026-03
  to flatten the then-`<Link><Button>` wrapper, and the 2026-08 migration left
  it stripping the card's primary "Edit" to a bare text link. Removed, with a
  source-sweep guard in `ButtonLink.test.jsx`.
- **Only a plain left click is intercepted.** A cmd/ctrl/shift/alt or middle click
  falls through to the real `href`, so open-in-new-tab keeps working. Losing that is
  the usual price of hand-rolling this, and it is exactly what a real link buys.
  Pinned by five cases in `ButtonLink.test.jsx`.

This flips the element's role, so a test looking for `getByRole('button')` on one of
these has to look for `link`. Seven assertions moved when the 25 landed, and each got
stronger for it: "this is a link" says more than "this is a button".

One caveat for anyone counting these: **a regex will undercount them.** The sweep that
found the first 23 missed two more whose `<Link>` held a ternary rather than a `<Button>`
directly. The runtime invariant found those; grep did not.

## OIUEEI Customization Layer

The project consumes HDS directly from npm and applies three local overrides:

- **Fonts** (`src/fonts/oiueei-fonts.css`) — the **Curiosa** variable font (`public/fonts/curiosa/Curiosa-Variable.woff2`, weight + italic axes), declared via `@font-face` honestly as `font-family: "Curiosa"` and served by Vite at `/fonts/curiosa/`. The HDS `--font-default` token's *value* is overridden to `"Curiosa", Arial, sans-serif` in `src/styles/oiueei-theme.css` — the token *name* is kept, so all HDS components resolve it transparently. The font binary is gitignored (licence); a clone without it falls back to Arial / system sans.
- **Colors** (`src/styles/oiueei-theme.css`) — CSS custom property overrides for the "Theeemes" color palette, imported after `hds-design-tokens` to take precedence.
- **Logos & brand assets** (`src/assets/`) — OIUEEI logos, placeholders, and favicon.

## Key Configuration (`vite.config.js`)

- **React deduplication** — Aliases `react` and `react-dom` to frontend's `node_modules` to prevent dual-copy hook errors (some HDS internal deps declare React 17 peer dep)
- **Proxy** — `/api` requests forwarded to `http://localhost:8000`
- **Dev server** on port 3000
- **A file of `public/` cited from JS goes through `import.meta.env.BASE_URL`** (`` href={`${import.meta.env.BASE_URL}cocina-ejemplo.zip`} ``). Production builds with `base: '/static/'` and Vite rewrites the paths it can see in `index.html` and CSS `url()`, but **not a literal inside JS**: `"/cocina-ejemplo.zip"` fell through to the SPA catch-all and downloaded the app's `index.html` under a `.zip` name (measured on www, 2026-09-29), while in development, where the base is `/`, both spellings are the same URL. A component test cannot tell them apart either — `BASE_URL` is `/` under vitest — so `test/publicFileLiterals.test.js` sweeps the source instead: no non-test `.js`/`.jsx` under `src` may hold a literal that opens with `/` + a name found in `public/` (the directory is read, not listed).
- **Code splitting** — every page is `React.lazy`-loaded in `App.jsx` (the `Routes` block is wrapped in a `Suspense` whose fallback is `LoadingSpinner`), so each route ships as its own chunk and page-only deps (papaparse, qrcode, jszip) load on demand. `build.rollupOptions.output.manualChunks` further splits `vendor-react` and `vendor-hds` from app code for long-term caching (`chunkSizeWarningLimit` is raised to **650 kB** because the shared `hds-react` chunk is **~622 kB raw / ~161 kB gzipped** — measured 2026-08-17, and it grows by a few kB each time a new HDS component is adopted: 585 → 614 on the 6.0.4 → 6.0.5 upgrade, 615 → 622 on taking `SelectionGroup`. Tree-shaking does work — `CookieConsent`, `Hero`, `Footer`, `Pagination`, `Stepper`, `Tabs` and `Breadcrumb` are absent from the built chunk — so the size is what we genuinely use).
- **A tab open across a deploy reloads once instead of dying** (`src/utils/reloadOnStaleChunk.js`, installed in `main.jsx` before the first render, 2026-09-29). A Heroku release ships only the *new* hashed chunks, so a tab opened before it asks, on its first visit to a page it had not loaded, for a chunk that is gone; `lazy()` rethrows and the top-level `ErrorBoundary` replaced the whole app with "Something went wrong" for a page that was fine a minute earlier. Vite dispatches a cancelable `vite:preloadError` on `window` when a dynamic import fails (present in the built `index-*.js`, checked); the listener records the time in `sessionStorage` under `staleChunkReloadAt`, calls `preventDefault()` and `location.reload()`, which fetches the current `index.html` and with it the current chunk names. **The reload only helps if `index.html` is fetched afresh**, so `spa_index` (`config/urls.py`) serves it with `Cache-Control: no-cache` (2026-09-29; `test_spa_index.py`) — without it a CDN in front, or a browser's heuristic, could hand the reload the very page that names the chunks that are gone. **One reload per 10 s, never a loop**: a second failure inside the window is *not* prevented and reaches the `ErrorBoundary` as before, so a chunk that is really gone (a broken release) cannot spin the page. And **when the mark cannot be read or written the page is not reloaded** — blocked storage, quota, private mode, even a `SecurityError` on merely touching `sessionStorage` (all in try/catch, the lookup lazy so installing can never stop the app rendering) — because reloading without being able to remember it is the loop being avoided. This is the app's only `sessionStorage` key, so README §Privacy's inventory now names it (it used to say "unused") and `test/browserStorage.test.jsx` pins both: one module may mention `sessionStorage`, its key is the one the README lists. The README half runs only in the standalone (`src/deployment/` exporting empty stubs): a deployment keeps every source file but replaces `README.md` and publishes its storage inventory in its own legal page, so it guards that inventory itself (reading the root README unconditionally failed the first deployment to merge this key, 2026-09-30). Unsaved input on a page that had *not yet* failed is not at risk (only unloaded chunks fail); tested in `reloadOnStaleChunk.test.js`, not in a browser.

## Authentication Flow

1. User enters email on `/login`
2. Backend sends magic link email pointing to `localhost:3000/verify/{rsvp.token}` — the high-entropy token, never the 6-char RSVP code
3. `/verify/:code` calls the backend, which sets JWT tokens as HttpOnly cookies on the response
4. `userCode` is stored in `localStorage` (for ownership checks only — auth tokens are never in localStorage)
5. Authenticated pages use `credentials: 'include'` to send cookies automatically. On 401, `apiFetch` silently attempts token refresh via `POST /api/v1/auth/refresh/`; if the session is gone it redirects to `/login?next=<the page>` and the magic link brings the reader back to it
6. `userCode` is used to determine ownership (e.g. hide reservation button on own things)
7. CSRF cookie is obtained on app load via a GET to `/api/v1/auth/me/` — a plain `fetch`, deliberately not `apiFetch` (a signed-out visitor's 401 must not trigger `apiFetch`'s refresh-then-redirect-to-login). Since 2026-09-15 this same call also applies a signed-in visitor's own saved `language`, if set, via `i18n.changeLanguage` — the top tier of the hierarchy `useCollectionLanguage` (above) otherwise only ever vetoes, never actively applies.
